# Operational quality, security qualification and recovery

Canonical domain contract. Owner: SRE / Security / QA. Implementation state: NOT_STARTED.


## Observability and service objectives

Instrument request → job → source query → batch → accepted RAW → dbt publication → serving response with correlation IDs. OpenTelemetry emits sanitized traces/logs to the approved AWS observability stack; Dagster run/event metadata supplements operational telemetry. Do not log literal SQL or credentials. Bound tenant/resource cardinality; detailed tenant diagnosis belongs in access-controlled logs and analytical operational facts. Dashboard owners, alert thresholds, silence policy and runbooks are release artifacts. (amended 2026-09-28, G-OPS-01, G-OPS-18) Operational foundations are built first, not at M9: the telemetry contract and library (log schema with forbidden keys, error taxonomy, W3C trace propagation through HTTP, outbox, SQS, ECS, Dagster and QUERY_TAG, metrics registry with a closed dimension list and ≤ 500 custom series per environment) in P1/M1, alert routing and on-call (OPS-102), the tombstone log (OPS-104) and SOC 2-ready evidence (OPS-108) in P1/M1, the first PITR drill in P1/M2, operator tooling and cost-attribution tags in P2/M3, SLOs and analytical recovery in P3/M5, the deletion workflow in P5/M7; M9 keeps only final qualification ([OPS backlog](../22-implementation-readiness/backlog/OPS.md) §4.0). Tenant, account and batch IDs appear only in structured logs and internal Snowflake ops facts, never as metric dimensions.

Initial internal targets, measured before offering contractual SLAs: API availability99.9% monthly; warm interactive p95≤2s, cold p95≤10s, hard query deadline15s; auth/control error rate<1%; publish fresh accepted data within30min after source availability for ordinary partitions; backlog age and source lag are reported separately. (amended 2026-09-28, D-31, G-OPS-02…04) Objectives: **control plane (login, settings, onboarding, health and other non-Snowflake endpoints) 99.9 %**, **analytical reads 99.5 %** (28-day rolling), because analytical reads cannot exceed Snowflake's own 99.9 % commitment; dependency-caused minutes still count but are classified `cause=dependency:snowflake`. Availability SLIs combine real requests with synthetic probes (1-min API probe, 5-min login probe) and burn alerts evaluate only windows with ≥ 50 valid events, so one failed request at low traffic cannot page and missing probe data alarms instead of reading as 100 %. "Source availability" is not observable in customer accounts, so the freshness SLO **FRESH-1** measures Bridge processing latency `publication_committed_at − manifest.committed_at` (p95 ≤ 30 min); end-to-end freshness is a reported decomposition, measured exactly only on canary accounts, and with hourly account-cycles (D-08) product copy states that query data is typically 1–2 h behind the source. Warm = Bridge result-cache hit; cold = cache miss executed by the broker, including warehouse resume. The SLO catalog is OPS-003's. Backfills and reports use independent queues and quotas. Financial completeness and source permission gaps are not hidden inside API uptime. Synthetic canaries use two synthetic tenants and never mutate customer workloads. (amended 2026-09-28, G-OPS-05, U-03, D-32) Canaries run on the single non-production Snowflake estate owned by INF-101 (≤ 150 credits/month) with a deterministic hourly workload and **lagged** oracles — query count at H+2 h, metering row at H+7 h, Σ query-attributed + idle = metered compute at H+10 h — because Account Usage latency makes a "last hour" check fail by construction; the estate's organization account is **tenant zero**, whose real usage statement verifies billing semantics (FIN-108).

Quality levels: transport checksum/count/schema, transformation uniqueness/relationships/coverage, financial conservation/authority/reconciliation, and semantic/API parity. A failed required quality check blocks that partition's publication and preserves the previous accepted revision. Partial availability remains explicit. (amended 2026-09-28, G-OPS-17, U-19) The gate catalog (T transport, X transformation, F financial, S semantic families; REQUIRED or ADVISORY) is OPS-002's; results live in one store, `QUALITY.CHECK_RESULT`, keyed by candidate revision; ERROR or a missing result counts as FAIL; gating is per tenant under D-06 ([ADR-014](../architecture/adr/ADR-014-analytical-revisions.md)). Every alert names the owner, impact, first failing durable state and safe recovery action.

## Backup and recovery design

Aurora PostgreSQL: encrypted automated backups/PITR with35-day retention and deletion protection; daily protected snapshots under approved retention; restore into a new cluster, validate RLS/migrations/outbox fences, then controlled endpoint cutover. Target RPO≤5min and RTO≤4h for a same-region control-plane incident, demonstrated by a timed drill. [Aurora PITR](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/aurora-pitr.html). A restore rolls back business workflow too: reconcile delivered notification/report IDs before resuming dispatch to avoid replaying old side effects. (amended 2026-09-28, G-OPS-08) The external truth is an append-only S3 dispatch journal of provider-accepted deliveries; the first post-restore write bumps a global lease epoch so fencing tokens minted before the restore are rejected; coverage is re-derived from Snowflake acceptance and S3 manifests before schedulers resume; mutations lost in the restore window are listed from the S3 audit export. Redis is rebuilt; losing it must not lose accepted jobs, leases or permissions.

S3 journal retention90 days alone cannot recover400 days of facts. (amended 2026-09-28, D-26) Journal and RAW retention are now 400 days for FINANCIAL sources and 90 days for QUERY_GRAIN sources, which narrows but does not remove the gap. Therefore create a daily consistent canonical analytical recovery snapshot covering all retained ledger/history/config versions and required closed-statement evidence, with publication manifest/checksums. (amended 2026-09-28, G-OPS-06) Physical design in three tiers ([ADR-011 amendment](../architecture/adr/ADR-011-analytical-recovery.md)): Tier 1 Snowflake Backups of the ledger, serving, config and security databases (daily, 35-day expiry, no retention lock; GA since 2025-12-10, same account and region only); Tier 2 incremental Parquet export of new immutable revisions to an S3 bucket in a separate AWS recovery account, with a daily recovery manifest (publication map, per-revision row counts, `HASH_AGG`, per-currency sums, `tombstone_hwm`); Tier 3 (R2, owner decision) replication to a second EU account. Zero-copy clones cannot cross accounts. Store encrypted private snapshots for35 days in a separate restricted recovery location. Preserve longer evidence according to contracted policy. A snapshot plus subsequent accepted journal restores the current state; raw history older than90 days is not promised as raw replay. Test an old partition outside raw retention. Snowflake Time Travel is useful short-term protection, not the sole disaster-recovery strategy. Confirm edition/retention and actual central account recovery options before launch. Optional Snowflake replication or approved S3 cross-region backup is a separate residency/cost decision, with measured replication lag; do not claim zero-loss regional failover by default. [S3 replication](https://docs.aws.amazon.com/AmazonS3/latest/userguide/replication.html).

Analytical target RPO≤24h for daily snapshot-only old-history changes, and no loss of acknowledged S3 batches within the surviving journal; RTO≤8h for the benchmark footprint. Measure actual values. Recovery in a new Snowflake account must recreate WIF users, storage integration trust, row policies, manifests and current permission profiles. Traffic remains blocked until isolation, totals and watermarks are verified. Reapply deletion tombstones and revoke obsolete identities before serving recovered data. (amended 2026-09-28, G-OPS-07, D-10) Tombstones live in the append-only OPS-104 log (PostgreSQL plus an S3 mirror in the security/log-archive account, outside every restore scope); each restore replays the full log before enabling traffic, and tenant offboarding schedules deletion of the tenant's KMS key so that pseudonym dictionaries in backups become unreadable. Recovery recreates the D-02 identity model (tenant users, profile roles, entitlements). OPS-007 moves to P3/M5 so the first analytical restore drill precedes the query-grain journal horizon.

## Scale and internal economics

Benchmark profile:100 tenants, each5 accounts, up to1M queries/account/day,365 days requested history; plus a burst from one tenant at10× steady rate. (amended 2026-09-28, G-OPS-11) Capacity is staged: **C1** (R1 launch gate, executed) = 10 tenants × 5 accounts, median 300k queries/account/day, p90 1M, one skew account at 3M/day, two tenants backfilling 365 days while eight are steady, 30 concurrent interactive users, 50 report runs/day; **C2** (R2, executed) = 50 × 5; **C3** = this PRD profile by extrapolation plus one live bottleneck test. Admission quotas come from C1 measurements and are enforced by LCH-101 entitlements. Start below this load, document actual capacity and refuse unsupported quotas. Partition pruning, aggregate marts, fair queues, streaming extraction, file sizing and bounded concurrency must be tested with skew. No need to load182.5B synthetic rows just to claim the target: publish both representative executed volume and extrapolation assumptions, then test the bottleneck with an approved live benchmark budget.

Measure AWS CUR/cost allocation, ECS runtime, network/NAT, S3 operations/storage, central Snowflake compute/storage/Snowpipe, observability, messaging and support allocation. Internal operational cost facts live in a separate Snowflake namespace inaccessible to customers. PostgreSQL stores plans/entitlements/commercial references only. Shared cost allocation uses declared drivers and an explicit unallocated bucket. (amended 2026-09-28, G-OPS-12, D-06) Because dbt builds are multi-tenant, a per-tenant query tag exists only on single-tenant work (refines PRD §139): serving compute is attributed exactly by the tenant's WIF serving user; transform compute per build and model is split by rows written per tenant (ORC-104, from `PARTITION_REVISION`); Snowpipe credits are split by manifest bytes (exact at 0.0037 credits/GB); storage by tenant row share (labelled estimate); AWS by CUR `component` tag, ECS task-seconds and extracted bytes. Customer-side extraction credits (D-08) are the customer's disclosed "Bridge overhead", never Bridge COGS. Cost guardrails (budgets, anomaly detection, CUR 2.0 export, cost-trap policy checks) exist from P0 (INF-105) with a baseline cost model, and non-production Snowflake spend is capped at 500 credits/month (D-32). Gross margin=(recognized revenue−allocated COGS)/recognized revenue; zero revenue → null margin. Fixture: revenue1000, compute100, AWS120, support80 givesCOGS300 and margin70%. Revenue recognition/accounting treatment requires finance approval before external reporting; estimates are labelled.

## Security qualification and support

Threat tests cover BOLA/IDOR, SQL injection, cross-tenant cache/cursor/job/report leakage, Cognito/JWT confusion, CSRF/session fixation, webhook SSRF, scope revocation, S3 prefix/IAM escape, Snowflake CURRENT_USER policy bypass, administrative identity separation and supply-chain vulnerabilities. No unresolved critical/high exploit with tenant disclosure may launch. Audit store access, retention/deletion and support access are tested. (amended 2026-09-28, G-OPS-14, D-25) An external grey-box penetration test (OPS-107, booked at P4) is retested before the release candidate; `/.well-known/security.txt` and a vulnerability disclosure policy ship in R1; SOC 2-ready controls generate evidence continuously from P1 (OPS-108: change management, quarterly access reviews, vulnerability SLAs, backup drills, incidents, vendor register); certification timing remains a business decision. Support access is time-bound, reason-coded, approved by customer policy and audited; no shared admin passwords or unaudited impersonation. (amended 2026-09-28, C-15, U-05) Support access is a tenant-approved read-only synthetic membership (default 4 h, maximum 8 h, scopes `health_read`/`analytics_read`; SEC-104) used through the single ops plane (CTL-102) and the `bridge-admin` CLI (OPS-106) with a two-person break-glass procedure.

Use [operational runbooks](RUNBOOKS.md) for diagnosis and recovery. Exercises record start, detection, owner, containment, restoration, expected/observed totals, customer impact and corrective task. Incident severity is based on actual exposure/availability, with a named incident commander and communication owner. (amended 2026-09-28, D-37, G-OPS-16) Support at launch is **EU business hours, Monday–Friday 09:00–18:00 CET**, with SEV1 (suspected disclosure, total outage, broadly served financial corruption) paged on a best-effort basis outside those hours; there is no contractual 24×7 commitment until a staffed rota exists. The paging tool must have a supported future (not Opsgenie, whose support ends 2027-04-05), and every alarm carries owner, severity, runbook URL and impact tags. This documentation does not send notifications or grant support access.
