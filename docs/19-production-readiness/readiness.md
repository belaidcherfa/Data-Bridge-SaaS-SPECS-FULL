# Production readiness and release qualification

Canonical domain contract. Owner: Delivery manager / DevOps / Security. Implementation state: NOT_STARTED.


## Promotion and rollback contract

Build once, promote immutable image digests and pinned schema/dbt/config manifests through development, staging and production. (amended 2026-09-28, G-REL-01, G-REL-08) Production is not first provisioned at M10: a "dark production" (REL-104, phase P3) receives every weekly candidate through the same pipeline with sign-up disabled, only canary tenants, production probes and paging live, and the NAT Elastic IPs published to customers allocated once (D-09). The release manifest v1 lists every behaviour-bearing artifact: image digests (API, broker, BFF, workers, extractor, launcher, Dagster components, renderer), migration head, dbt manifest and package lock, `serving_schema_version`, source/metric/gate registry versions, Terraform plan digests and the feature-flag snapshot ([REL backlog](../22-implementation-readiness/backlog/REL.md) §3). GitHub Actions uses OIDC with repository/ref/environment conditions; customer data never enters CI. Required promotion checks include contract compatibility, migration rehearsal, numerical fixtures, tenant isolation, IaC plan review, image/SBOM/signature validation and evidence freshness. Production configuration is explicit, not copied from developer machines.

Use expand → deploy compatible readers/writers → migrate/backfill → verify → contract for PostgreSQL and analytical schema changes. (amended 2026-09-28, G-REL-02, C-16) Migrations are forward-only, linted in CI against a forbidden-operation list, run as a one-off task under an advisory lock with `lock_timeout=3s` and retries, and a contract step is refused while any older worker generation is still running; an N−1 compatibility job runs the previous release's tests against the new schema. Old and new worker generations cannot concurrently advance the same fenced lease. dbt writes candidate revisions, runs gates, then swaps the publication pointer — (amended 2026-09-28, ADR-014) the "swap" is the DML-only `PUBLISH_BATCH` compare-and-swap over the publication map, never DDL. Reverting code must not silently roll back accepted customer mutations or closed finance. Rollback options are previous application digest, previous compatible publication, paused ingestion, or a forward data repair. (amended 2026-09-28, G-REL-03, C-21) "Compatible" is defined by versioned serving namespaces: each publication records `serving_schema_version`, each API build supports {n−1, n}, a pre-deploy check refuses a digest that cannot read every tenant's current publication, and a previous publication is restored by forward republication. (amended 2026-09-28, G-REL-04…06) API, broker and BFF use ECS blue/green with a smoke hook (synthetic login, isolation probe, 270 fixture); workers roll with SIGTERM drain and lease fencing; the Dagster daemon is stop-then-start; feature flags and kill switches are server-side and audited (REL-102); production changes follow a weekly train with a financial-logic freeze from the last business day of a month to month end + 5 days. Destructive migrations require a separately reviewed recovery plan and data evidence.

Production launch is gated by [readiness checklist](CHECKLIST.md). A release candidate is an immutable version plus exact artifact digests, infrastructure plan, dependency lockfiles, task/evidence matrix, accepted capability limitations, rollback owner and customer communication plan. Missing required security or numerical evidence blocks promotion. Vendor outages and unavailable optional capabilities are documented; they cannot be converted into a false PASS.

Customer-facing availability begins only after production synthetic login, organization isolation, WIF, ingestion,270-USD fixture reconciliation, report access and alarm tests succeed. These are controlled synthetic fixtures, not assertions about real customer cost. (amended 2026-09-28, U-03, G-INF-01, G-GOV-01) Live evidence additionally includes **tenant zero** (the organization account of the INF-101 test estate): parity between direct Account Usage/Organization Usage queries and Bridge's journal/RAW for windows older than the maturity horizon, and one month of currency billing reconciled against its real usage statement (FIN-108); the corrected distinct-window monitor fixture of the [validation strategy](../15-testing/validation-strategy.md); and the restore drills of the recovery tiers. Evidence freshness is bounded: live Snowflake suite 7 days, isolation suite 30 days, restore drills 90 days, capacity C1 90 days, external penetration test 12 months (G-REL-07). Legal/commercial readiness includes terms, privacy/retention agreement, subprocessors, support contacts, billing currency/tax handling and security questionnaire evidence reviewed by the responsible human owners. Documentation does not constitute legal advice or signed agreements. (amended 2026-09-28, D-17, D-25, D-30, D-36, D-37) The pack states the plan model (platform fee + spend band, USD, contracted pilot), the invoicing channel (manual invoices or a Stripe payment link from a tool that meets French VAT and e-invoicing obligations, confirmed by an accountant — the invoicing entity is French), SOC 2-ready control evidence (certification later), the EU processing region and the support policy (EU business hours, SEV1 best effort, no contractual 24×7).
