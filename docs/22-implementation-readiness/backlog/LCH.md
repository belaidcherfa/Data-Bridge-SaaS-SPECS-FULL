# LCH — Implementation-readiness review and production backlog

Canonical contract: [launch.md](../../20-launch/launch.md), [ADR-012](../../architecture/adr/ADR-012-first-customer-commercial.md), [MILESTONES M10–M12](../../../MILESTONES.md), [readiness.md](../../19-production-readiness/readiness.md) (legal/commercial readiness paragraph). Tasks reviewed: LCH-001, LCH-002, LCH-003, LCH-004. Reviewer: domain audit agent, 2026-09-27. Status of all tasks: NOT_STARTED.

## 1. Verdict

Not implementable in its current order. The principle is right (trial, signed order and settled payment are distinct; manual B2B invoicing; no fabricated paid state), but the graph puts "first production release" (LCH-003) after payment (LCH-002), which comes after the first customer has already been onboarded on production (ONB-003..005) — the go-live is inverted. Entitlements, needed for admission from M2, are defined at M10. The subscription state names differ between CTL-007 and launch.md. There is no legal pack (ToS/DPA/subprocessors/transfers), no VAT/numbering model and no answer to the French e-invoicing reform, which is live since 1 September 2026 (VERIFIED) and, if the company is French, dictates that invoices are issued through an approved platform rather than generated by the product. Author first: the canonical subscription state machine with effect matrix, the plan-agnostic entitlement model (LCH-101), and the owner's legal-entity/tax facts (LCH-103-S01).

## 2. Findings

### G-LCH-01 · Go-live happens after the first customer is already in production
Severity: BLOCKER · Type: CONTRADICTION
Evidence: `task-index.json` — LCH-003 deps `LCH-002, REL-004`; LCH-002 deps `ONB-005, LCH-001`; ONB-003 deps `REL-004` (real customer on production at M11); `launch.md` — "Rollout starts with synthetic smoke checks and the approved first customer; monitor before expanding. Post-launch checks: hourly during the first working day".
Why it matters: the hourly first-day monitoring, rollback thresholds and release record would start weeks after the customer's data is already being collected and served; the "monitored rollout" never covers the riskiest period (first real connection, first backfill, first reconciliation).
Resolution: re-scope LCH-003 to "Production go-live for the first customer (monitored rollout)" with deps `REL-004` only, and add `ONB-003 +LCH-003`. LCH-002 (verified payment) stays the M12 commercial gate and no longer precedes deployment; LCH-004 deps `LCH-003, ONB-004`. This challenges MILESTONES M12 ("First production release"): go-live moves to the M10/M11 boundary; M12 becomes "first paying customer verified + reviews".
Affects: LCH-002, LCH-003, LCH-004, ONB-003.

### G-LCH-02 · Entitlements are defined at M10 but enforced from M2
Severity: HIGH · Type: GAP (dependency)
Evidence: `LCH-001` — "show limits before costly backfill admission" (M10); `semantic-api.md` — "queue admission is plan-aware"; `CTL-007` (M1) — "entitlement lookup required before gated features/jobs"; D-17 — "Entitlement design must be plan-model-agnostic: quotas = (connected_accounts, users, history_days, report_schedules, api_clients)".
Why it matters: ING-010, API-004/006, RPT-004, CTL-003 and ONB-001 each invent their own limit checks, or ship without limits and are retrofitted at M10.
Resolution: new LCH-101 at M2 (extends CTL-007): plan catalogue with the D-17 quota vector plus `query_detail_days` (D-11), `heavy_jobs_concurrent`, `backfills_concurrent`; one `entitlements.check()` used by all admission points; LCH-001 keeps only billing operations.
Affects: new LCH-101, LCH-001, ONB-001.

### G-LCH-03 · Subscription state names conflict across specs
Severity: HIGH · Type: CONTRADICTION
Evidence: `CTL-007` — "Define subscription states TRIAL/ACTIVE/PAST_DUE/SUSPENDED/CANCELLED"; `launch.md` — "TRIAL → ACTIVE_PENDING_PAYMENT → ACTIVE_PAID; PAST_DUE/SUSPENDED/CANCELLED"; `21-ui-ux/pages/settings.md` — "BRIDGE SUBSCRIPTION: Pilot … PAYMENT STATUS: DEMO".
Why it matters: CTL-007 would implement a single ACTIVE state that cannot distinguish signed-but-unpaid from paid, which is the exact distinction ADR-012 relies on; "DEMO" is neither a state nor a status.
Resolution: canonical state machine (launch.md wins; CTL-007 migrates its enum): TRIAL → ACTIVE_PENDING_PAYMENT (signed order recorded) → ACTIVE_PAID (invoice fully covered by VERIFIED payments) → ACTIVE_PENDING_PAYMENT at renewal invoice; ACTIVE_* → PAST_DUE (daily job: due date passed, unpaid) → SUSPENDED (manual, four-eyes, after grace) → CANCELLED (term end/termination); TRIAL → SUSPENDED on trial expiry. "Pilot" is a plan name; DEMO exists only as `tenant.is_synthetic=true` and can never satisfy M12. Effect matrix:

| State | Reads/UI | Scheduled sync | New backfill/replay | Reports, monitors, notifications | Exports | New users/API clients |
|---|---|---|---|---|---|---|
| TRIAL | yes | yes | within trial quota | yes | yes | within quota |
| ACTIVE_PENDING_PAYMENT / ACTIVE_PAID | yes | yes | within plan | yes | yes | within plan |
| PAST_DUE | yes + Owner banner | yes | yes | yes | yes | yes |
| SUSPENDED | read-only | paused (no customer credits burned) | no | paused | yes (export window) | no |
| CANCELLED | Owner export only for 30 days | stopped | no | stopped | Owner only | no |

Data retention is independent: nothing is deleted by a state change; deletion only via OPS-005.
Affects: LCH-001, LCH-101; cross-domain CTL-007, UX settings page.

### G-LCH-04 · French e-invoicing reform is live and changes how invoices must be issued
Severity: HIGH · Type: VENDOR-FACT / GAP
Evidence: `ADR-012` — "Use approved manual B2B invoicing"; `launch.md` — "billing currency/tax handling" (no detail). VERIFIED (entreprendre.service-public.gouv.fr/actualites/A15683, ey.com tax alerts, vatcalc.com, avalara.com — search snippets 2026-09-27): from 1 September 2026 all companies established in France must be able to receive electronic invoices; large companies and ETIs must issue them from 1 September 2026, SMEs and micro-enterprises from 1 September 2027; exchange goes through an approved platform ("plateforme agréée", formerly PDP) with the PPF acting as directory and data concentrator; e-reporting of cross-border B2B and B2C transaction data follows the same two waves; payment data must be reported where VAT is due on collection (typically services); new mandatory invoice mentions from 1 September 2026 include the customer's SIREN, delivery address if different, operation category (goods/services/mixed) and the VAT-on-debits option.
Why it matters: if Bridge's legal entity is French, a PDF invoice generated by the product would be non-compliant for French B2B customers once Bridge's issuance wave applies (2027 for an SME), and the PA must receive the "collected" payment status for services; building invoice generation in-app would be wasted and risky.
Resolution: R1 does not generate invoices in the product. The owner selects an accounting/invoicing tool connected to an approved platform (LCH-103); Bridge stores invoice references (number, date, amounts, VAT treatment, PA transmission id and lifecycle status) and payment evidence only. If the entity is not French, LCH-103 records the applicable regime instead (owner question 1). All wording and obligations TO VERIFY with the company's accountant.
Affects: LCH-001, new LCH-103.

### G-LCH-05 · No invoice, VAT treatment, numbering or credit-note model
Severity: HIGH · Type: GAP
Evidence: `CTL-007` — "subscription stores status/plan/entitlement versions and invoice metadata only"; `LCH-001` — "duplicate reference guards and correction review".
Why it matters: "invoice metadata" does not say which invoice identifies a payment, how partial payments or credit notes affect ACTIVE_PAID, or how a reverse-charged EU invoice differs from a domestic one; finance corrections by editing records destroy the audit trail.
Resolution: `commercial.invoice_refs` and `commercial.payment_events` (§3): unique `(issuer_entity, invoice_number)`; VAT treatment enum `DOMESTIC_STANDARD`, `EU_B2B_REVERSE_CHARGE` (customer VAT ID validated, mention per Art. 196 of Directive 2006/112/EC), `NON_EU_OUT_OF_SCOPE`; issued invoices never edited — corrections by credit note (`credit_note_of`); payments allocated to invoices, partial payments keep ACTIVE_PENDING_PAYMENT; reversal is an append-only event. Numbering is the invoicing tool's responsibility (unique, chronological series; TO VERIFY with accountant); Bridge validates uniqueness only.
Affects: LCH-001, LCH-103.

### G-LCH-06 · Legal and privacy pack has no owning task
Severity: HIGH · Type: GAP
Evidence: `readiness.md` — "Legal/commercial readiness includes terms, privacy/retention agreement, subprocessors, support contacts, billing currency/tax handling and security questionnaire evidence"; grep "DPA", "subprocessor", "GDPR" in `docs/**` → no hits outside that sentence.
Why it matters: the customer's procurement cannot sign without a DPA (GDPR Art. 28(3) mandatory content), a subprocessor list and a transfer position; security questionnaires need a whitepaper and pentest letter. These have multi-week lead times on the customer side (P0 in ONB timeline).
Resolution: new LCH-102 (M8): DPA annexes (subject matter, duration, nature/purpose, data types: Snowflake account-usage metadata incl. pseudonymized user identifiers (D-10), sanitized query text, object/role names; Bridge user names/e-mails; data subjects: customer staff), TOMs, subprocessor register — AWS (hosting, incl. Cognito, SES, CloudWatch; EU region) and Snowflake (central analytical store; EU region), plus any paging/status/helpdesk tool that receives personal data; Slack, Microsoft Teams, customer webhooks and recipient mailboxes are customer-directed destinations disclosed separately, not Bridge subprocessors; transfer mechanism for US-parented vendors (EU-US Data Privacy Framework and/or SCCs 2021/914 in their DPAs) with counsel's transfer assessment — TO VERIFY with counsel; processor breach notice to controller ≤ 48 h to support the controller's 72 h (Art. 33); subprocessor change notice ≥ 30 days with objection right; security whitepaper and questionnaire answers.
Affects: new LCH-102, REL-003, ONB-003.

### G-LCH-08 · Support model and SLA stance undefined for a small team

### G-LCH-09 · Price is owner input but the cost floor is unknown to the commercial workflow

Why it matters: a plan priced below the per-tenant floor loses money at R1 scale; customer-side credits (≈ 18–24 credits/month per account, G-ONB-02) are an additional cost the buyer will compare.
Resolution: LCH-001-S01 records the owner's plan decision together with the OPS-009 floor inputs and the disclosed customer-side footprint; pricing itself remains an owner decision.
Affects: LCH-001.

### G-LCH-10 · Payment verification lacks four-eyes on the activating event

Why it matters: a single operator can create a false ACTIVE_PAID (failure scenario "False paid marker" in LCH-001) without any correction ever being reviewed.
Resolution: `VERIFIED` requires `verified_by ≠ recorded_by` for every payment, not only corrections.
Affects: LCH-001, LCH-002.
