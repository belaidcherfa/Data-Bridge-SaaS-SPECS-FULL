# ADR-014 — Analytical revisions and publication

Status: Accepted for implementation (owner decision record 2026-09-28: D-05, D-06); physical benchmark DBT-101-S09 NOT_RUN. Date: 2026-09-28.

## Context

The orchestration contract asks for coherent published versions ("no user sees a half-new ledger/half-old allocation snapshot"), while the transformation contract describes MERGE with per-tenant/dataset/partition leases. The two were never reconciled, and nothing defined how a serving query selects the published revision under a row access policy, how superseded revisions are garbage-collected while statements pin them, or how hundreds of tenants publish without one dbt run each ([audit](../../22-implementation-readiness/AUDIT_CROSS_CUTTING.md) X-11; blockers G-DBT-01 and G-ORC-06).

Verified vendor behaviour constrains the design:

- dbt-snowflake `insert_overwrite` clears the whole target table before inserting (VERIFIED, dbt-adapters source); `microbatch` deletes a time slice for **all** tenants and reinserts; `merge` and `delete+insert` mutate rows in place, destroying the version a pinned cursor or report reads.
- In Snowflake a DDL statement implicitly commits the active transaction (VERIFIED), so `CREATE OR REPLACE`, `ALTER TABLE … SWAP` or view replacement cannot take part in an atomic per-tenant publication.
- DML locks block only concurrent DML on the same rows; parallel per-tenant MERGEs still rewrite micro-partitions shared with other tenants unless tables are clustered by tenant and date.

## Decision

1. **Insert-only revisioned partitions.** Ledger, attribution, allocation, serving and Python-output facts live in revision tables `*_R(tenant_id, scope_id, partition_start, revision_id, build_id, …business columns)`, `CLUSTER BY (tenant_id, partition_start)`, `DATA_RETENTION_TIME_IN_DAYS = 1`, with the row access policies of the [ADR-005 amendment](ADR-005-analytical-authorization.md) attached to the base tables. Rows carry `revision_id` and `build_id`, never `publication_id`. The partition grain is declared per dataset in `data/contracts/datasets.yaml`: query-grain facts (account, **hour**), charges/attribution/allocation/serving (scope, **day**), monthly marts (tenant, month), Python outputs (tenant, as-of day).
2. **Custom `revisioned` dbt materialization.** One DML-only transaction: delete this build's own unpublished rows (retry idempotency), `INSERT … SELECT` restricted to the build workset and ordered by `(tenant_id, scope_id, partition_start)`, register every workset partition in `PARTITION_REVISION` (row count, `HASH_AGG` checksum, snapshot_seq, code and config versions), **including zero-row partitions** so a correction to empty removes old rows. It calls dbt's contract assertion and refuses `--full-refresh`. `revision_id` comes from a PostgreSQL sequence.
3. **Staging is read-time deduplication.** Staging models are views over accepted RAW (`accepted_source()` with `accepted_seq <= snapshot_seq`), deduplicating by natural key or by selecting one accepted window snapshot; there is no MERGE in R1. MERGE is a fallback only if the DBT-101 benchmark shows read-time deduplication is too costly.
4. **Multi-tenant set-based builds (D-06).** A processing ledger tracks accepted-but-unprocessed batches (`BATCH_PROCESSING`), each build records `snapshot_seq`, `BUILD_WORKSET` lists exact partitions and `BUILD_CONFIG_PIN` pins each tenant's configuration version ([ADR-007 amendment](ADR-007-rule-publication.md)). The only dbt variable is `build_id`. One build runs per cadence (trigger: oldest unprocessed batch ≥ 10 min or ≥ 500 batches); per-tenant runs are reserved for targeted replay and repair.
5. **Per-tenant publication gating.** Tenant-scoped invariants are check models writing one PASS/FAIL row per (candidate revision, tenant, check) into `QUALITY.CHECK_RESULT`; absence counts as FAIL. ORC-005 is the only eligibility evaluator. A tenant whose checks fail keeps its previous pointer while other tenants publish. Runtime errors are bisected by tenant halves in the repair lane; a tenant gated three consecutive builds is quarantined from the steady lane.
6. **SCD2 publication map and one compare-and-swap.** Tables `PUBLICATION.TENANT_POINTER`, `PUBLICATION`, `PUBLICATION_MAP(tenant_id, dataset_id, scope_id, partition_start, revision_id, valid_from_seq, valid_to_seq)`, `DATASET_VERSION`, `CANDIDATE_CHANGE`, `BUILD`, `LANE_FENCE`, `PIN`. A single publisher (PostgreSQL lease) allocates a global monotonic `pub_seq` and calls `PUBLISH_BATCH(pub_seq, build_id, fence_token)`, which in one DML-only transaction verifies the build is VALIDATED and its fence equals `LANE_FENCE`, compare-and-swaps all eligible tenants' pointers set-based (updated rows must equal eligible tenants, else rollback), closes superseded map rows, inserts new ones, bumps `DATASET_VERSION` only for changed datasets and marks the publication PUBLISHED. Return codes: PUBLISHED, ALREADY_PUBLISHED, FENCED, CONFLICT, NOT_VALIDATED. A tenant is published only when all its affected partitions are at the same code version (shadow rebuild homogeneity). Rollback is a forward publication re-pointing to prior revisions (`REPUBLISH_PRIOR`); the pointer never decreases.
7. **Pinned reads.** Readers pin `pub_seq`; secure serving views expose `_pub_from/_pub_to` and are filtered with `_pub_from <= :pin AND :pin < _pub_to`. Serving views are deployed by release migrations in versioned namespaces (`serving_schema_version`), never replaced by dbt runs. `dataset_version` is the `pub_seq` at which a tenant's dataset map last changed. PostgreSQL receives a monotonic acknowledgement (`platform.dataset_publication_refs`) and an outbox event `publication.advanced`; a reconciler replays missing acknowledgements from Snowflake and never writes Snowflake from PostgreSQL.
8. **Two-phase publication for Python outputs.** The dbt financial publication P is published first; Python engines read inputs pinned to P and their outputs are published in a later P′ with `input_pub_seq = P`. A Python failure never blocks ledger publication.
9. **Pins and garbage collection.** Long-lived holders (report and analysis jobs, statements, recovery snapshots, operator holds) create explicit `PIN` rows. Cursors create no pins and rely on a grace window of max(cursor TTL + 15 min, 7-day rollback window), with the TTL read from the API configuration key `cursor_ttl_seconds`. ORC-105's daily GC is the only physical deleter of revisioned rows: superseded, unpinned revisions past the grace window, orphan revisions of terminal builds after 24 h, and dataset retention expiry (D-11, D-26). A purged pin answers RESTART_REQUIRED (API 410 `PUBLICATION_RETIRED`).
10. **Cost attribution.** Central transform credits are allocated to tenants by rows written per tenant (`PARTITION_REVISION.row_count`), because a set-based build cannot carry one tenant's query tag.

## Alternatives considered

dbt `merge` or `delete+insert` in place: destroys pinned versions and rewrites shared micro-partitions. `insert_overwrite`: truncates the whole table (VERIFIED). `microbatch`: deletes a time slice for every tenant (VERIFIED). Table swap or `CREATE OR REPLACE`: DDL auto-commits and switches all tenants at once. One dbt run per tenant: hundreds of invocations per cadence and per-tenant compilation (rejected by D-06). Per-tenant tables or databases: object explosion and operational cost (ADR-001). A `publication_id` column on rows: forces copying unchanged partitions at every publication.

## Consequences

A custom materialization and a Snowflake Scripting procedure become core platform code with their own tests. Reads join a small clustered map; read amplification (live ÷ published revisions) is monitored and alarmed above 3. Map cardinality grows with hour-grain partitions: with 365-day query-level detail (D-11), 500 accounts × 24 × 365 ≈ 4.4 M map rows for the hour-grain dataset, to be confirmed by the benchmark. Snowflake does not enforce primary keys, so uniqueness and relationships are check models. Time Travel is 1 day on revision tables; rollback relies on superseded revisions retained ≥ 7 days and disaster recovery on [ADR-011](ADR-011-analytical-recovery.md). This ADR supersedes the MERGE and per-tenant lease wording in the transformation contract and makes the orchestration contract's "one Snowflake transaction advances the tenant publication pointer" precise.

## Revisit conditions

The DBT-101 live benchmark (≤ 200 credits) shows that read-time deduplication, pinned-read latency or GC cost exceed budget; Snowflake gains transactional DDL or a native per-partition swap; dbt gains a tenant-scoped atomic strategy with equivalent pin semantics.

## Validation obligation

DBT-101 benchmark evidence, ORC-005 compare-and-swap and fencing property tests, ORC-105 property tests proving GC never deletes a current or pinned revision, and retry-idempotency tests of the materialization.
